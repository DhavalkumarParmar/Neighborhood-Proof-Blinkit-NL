# Neighborhood Proof

A concept demo for Blinkit. On a product page, instead of star ratings, it shows
an honest summary of what households near that dark store actually did with the
product: how many bought it, how many sent it back, and what the recurring
complaint was.

**Live demo: https://neighborhood-proof-blinkit-nl.vercel.app**

**Concept demo, built for demo and educational purposes only. Not affiliated
with Blinkit.** That line appears at the bottom of every page in the app.

---

## Why

Repeat grocery buyers don't cross into beauty, pet, baby, home or electronics
because they lack conviction at the moment of consideration — not because they
can't find the products. Local, verifiable, complaint-inclusive proof is the
reason-to-believe.

Only Blinkit's dark-store density makes the local claim statistically sayable.
That is the moat: a competitor without stores every two kilometres cannot say
"212 homes near you", because it does not have 212 homes near you.

## Data flow

```
data/ledger.json          Row-level purchase + return records.
        |                 One row per household per SKU per store.
        v
lib/proof-core.ts         RETRIEVAL. Counts households, returns, return rate,
  (retrieval layer)       category baseline. Picks the reporting scope.
        |                 ---> every number on screen is produced here, in code
        |
        +-----------------> lib/copy.ts      Plain-language reads, in code
        |                                    ("that's low for beauty")
        v
lib/summarise.ts          LLM. Gemini receives the retrieved review strings and
  (summary layer)         the already-computed numbers. It returns one or two
        |                 sentences naming the recurring complaint. Nothing else.
        v
components/ProofCard.tsx  UI. Renders the numbers immediately from the server
  (proof card)            render; the model's sentence arrives afterwards.
```

### All numbers are computed in code and never generated by the model

This is the point of the architecture, so it is worth stating plainly:

- Household counts, return counts, return rates, the category baseline and the
  low/normal/high verdict are all computed in `lib/proof-core.ts` by counting
  rows in the ledger. No model is involved in producing any of them.
- The model is given those numbers as **read-only context** so its wording
  cannot contradict them. Its only job is to name the recurring theme in the
  review text.
- The model is forbidden from writing any digit at all, and `sanitise()` in
  `lib/summarise.ts` drops any sentence containing one. If nothing survives, no
  sentence is shown.

  This started as a narrower rule - allow figures we supplied, drop the rest -
  and the live model broke it immediately. Given a return rate of 4.2% it wrote
  "The return rate was 4.", which passed the guard because 4 was a number we had
  supplied, while being a naked figure that meant nothing. Banning digits
  outright removes the whole class of failure. The plain-language read beside
  every number ("that's low for beauty") is generated in `lib/copy.ts`, where it
  cannot drift from the arithmetic.
- The `/api/summary` route recomputes the facts server-side from the SKU and
  store. It does not accept numbers from the browser, so nothing the client
  sends can change a figure on the card.

If the model call fails for any reason — no API key, timeout, network error,
malformed response — the card renders its numbers alone. No error message, no
apology, no retry prompt. The numbers are the part that matters.

## The four display states

| State | Rule | What the card says |
|---|---|---|
| **Normal** | 30+ households at the store | "212 homes near you bought this last month · 9 sent it back. That's low for beauty." |
| **Widened to city** | under 30 at the store, 30+ city-wide | "Too few orders near you. Showing all of Vadodara instead." |
| **Honest negative** | return rate well above the category baseline | "11 of 38 sent it back. That's high." |
| **No data** | under 30 city-wide too | "New here. No orders yet to show you." |

All four are reachable in the deployed demo, and linked directly from the
profile picker on the home screen:

## The retrieval rules

```
households at store >= 30  ->  report at store scope
households at store <  30  ->  widen to the whole city, widened: true
households in city  <  30  ->  noData: true
```

Two details worth knowing:

- **The category baseline is network-wide, not per store.** A single store does
  not have the volume to make a per-category return rate mean anything, so
  "that's low for beauty" compares against every store in the network.
- **Reviews from people who returned the product are retrieved first.** When
  the list is trimmed to fit the prompt, a recurring complaint can never be
  trimmed out in favour of praise.

## Data

Synthetic, generated by `scripts/generate-data.mjs` with a seeded PRNG, so it is
reproducible. Regenerate with `npm run data`.

| File | Contents |
|---|---|
| `data/catalog.json` | 150 non-grocery SKUs across beauty, pet, baby, home, electronics, with ₹ prices |
| `data/stores.json` | 5 dark stores: Alkapuri and Gotri (Vadodara), Sector 62 and Sector 128 (Noida), Karjat |
| `data/ledger.json` | ~56,000 purchase records: household, SKU, store, date, returned, and a review string on some |
| `data/profiles.json` | 3 demo shoppers |
| `data/demo-pointers.json` | Which SKU demonstrates which state, emitted by the generator |

Brand names are invented. Real companies are deliberately not used, because the
return rates and complaints in this data are fabricated and should not be
attached to anyone's actual product.

**Complaints are gated by product traits.** Each SKU gets traits derived from its
name — `liquid`, `pump`, `gear`, `food`, `makeup`, `cleaner`, `battery` and so on
— and each complaint declares which traits make it possible. Without this, the
generator gave a cat scratching post dog-food reviews and a kajal pencil a broken
pump, which reads as obviously fabricated the moment anyone actually reads a card.
Praise is picked the same way.

Dates are stored as `daysAgo` (0–29) rather than absolute dates, so the "last 30
days" window stays true whenever the demo is opened instead of quietly emptying
out over time.

Volumes are tuned so all four states occur naturally rather than being special
cased. Three (SKU, store) pairs have pinned counts so the demo copy reads
exactly as designed — 212/9, 11/38, and the widened pet SKU. Everything else in
the ledger is generated.

### Why the low-density store matters

| Store | Density | Normal | Widened | No data |
|---|---|---|---|---|
| Alkapuri, Vadodara | high | 140 | 10 | 0 |
| Gotri, Vadodara | low | 100 | 50 | 0 |
| Sector 62, Noida | high | 136 | 14 | 0 |
| Sector 128, Noida | medium | 103 | 47 | 0 |
| Karjat | very low | 6 | 0 | 144 |

That last row is the argument for the moat in one line. At a dense store the
proof works for almost every SKU. At a thin one there is nothing honest to say
about 144 of 150 products, and the card says so.

## Running it

```bash
npm install
npm run dev              # http://localhost:3000
```

To enable the complaint sentence, set a Gemini API key:

```bash
echo 'GEMINI_API_KEY=your-key' > .env.local
```

Without a key, everything works except the one model-written sentence, which is
simply absent.

### Checks

```bash
npm run data              # regenerate the synthetic data
npm run check:retrieval   # asserts all four states are reachable, plus invariants
npm run check:summary     # figure guard and silent-degrade path
npm run build             # typecheck and production build

GEMINI_API_KEY=... npm run check:summary   # also exercises the live Gemini call
```

`check:retrieval` runs the real retrieval code against the real data and prints
the state census in the table above.

With a key, `check:summary` also prints the raw model reply next to what the
guard allowed through, so a bad key or an unavailable model is diagnosable. The
app degrades silently by design, which means misconfiguration otherwise looks
exactly like working-but-quiet — `diagnose()` in `lib/summarise.ts` exists only
for this script and reports the HTTP status and response body.

---

## Deploying

Vercel, no configuration needed. Set `GEMINI_API_KEY` as an environment variable
in the project settings, otherwise the complaint sentence will not render.

## Stack

Next.js 16 (App Router), React 19, TypeScript. No database — JSON files on disk.
No auth. No CSS framework; `app/globals.css` is hand-written to sit close to the
Blinkit app's yellow header, green Add buttons and sticky bottom bar. Okra is
proprietary, so the type falls back to the system sans stack.

The Gemini call is a plain `fetch` to `POST /v1beta/interactions` with model
`gemini-3.6-flash`, verified against ai.google.dev in July 2026 and confirmed
live (HTTP 200). Note that this is the current Interactions API, not the older
`generateContent` endpoint - code written from memory will target the wrong URL.

The UI is built to match screenshots of the app: light grey page with content in
white rounded cards, the yellow header with the delivery time and icon tab rail,
the ADD button inside the product image box, offers as plain blue text, and the
four-tab bottom bar. On the product page the star rating and review count are
removed and the proof card takes their place.

```
app/
  page.tsx              Screen 1 - profile picker, plus links to the four states
  browse/page.tsx       Screen 2 - browse listing, proof line computed per card
  p/[sku]/page.tsx      Screen 3 - product page, proof card under the price
  cart/page.tsx         Screen 4 - cart stub
  api/summary/route.ts  Recomputes facts, calls the model, returns one sentence
lib/
  proof-core.ts         Retrieval. Pure; takes data as arguments
  retrieval.ts          Wires proof-core to the JSON. Server only
  copy.ts               Numbers to plain English, in code
  summarise.ts          Gemini call, timeout, invented-figure guard
components/
  ProofCard.tsx         The card. Renders facts; does no arithmetic
  ComplaintLine.tsx     Client. Fetches the sentence; renders nothing on failure
  BrowseClient.tsx      Listing with search and category tabs
scripts/
  generate-data.mjs     Seeded data generator
  check-retrieval.mjs   State and invariant checks
  check-summary.mjs     Summary layer checks
```
